# Contributing to Nestworth

This guide describes the architecture, conventions, and testing expectations for anyone making changes to the codebase.

## 1. Architecture

### Local-First SQLite with Supabase Sync

Nestworth is a cross-platform personal finance app (iOS, web PWA, and macOS desktop via Electron) built with Expo SDK 54, React Native 0.81, React 19, and TypeScript 5.9.

- **Primary data store**: `expo-sqlite` (`lib/db.ts`). Single shared DB file `nestworth.db` with WAL journaling, opened once and shared by every caller, whose `withTransactionAsync` calls take turns (`lib/transactionQueue.ts`, #110). On web, expo-sqlite runs wa-sqlite (WASM) in a web worker over an OPFS file (its AccessHandlePool VFS) and provides the same API.
- **Remote sync**: Supabase (PostgreSQL + Auth + Realtime + Storage). Used for cross-device sync, not as the primary read path.
- **UI reactivity**: TanStack Query reads from SQLite. Mutations write to SQLite first (marking `_sync_status = 'pending'`), then call `requestPush()` to queue a background sync.
- **Routing**: Expo Router with file-based typed routes. `(auth)/` group for sign-in/sign-up, `(tabs)/` for the main app.

### Sync Engine (`lib/sync.ts`)

- **`requestPush`**: Pushes local `pending`/`deleted` rows to Supabase. Serialized by the `_syncInProgress` lock. A request that finds the lock held **by a sync for the same user** is queued (`_pushQueued`, or `_fullSyncQueued` for `fullSync`/`initialPull`) and every lock holder ends in `finishSync`, which drains the queue with the lock-free primitives, refreshes the pending count, and only then publishes `isSyncing=false` and releases the lock -- so nothing requested mid-sync is dropped (one holder drains at most `MAX_QUEUED_DRAINS` follow-ups; past that the flags stay set for the next trigger, and a caller awaiting that holder returns before its own sync has run), and the label reads `Synced` only when the count is fresh and zero. The drain clears `lastError` only before a full follow-up, which redoes the pull as well and re-reports a pull that is still incomplete (#66). A drained push cannot undo the holder's failure -- it neither retries a reset that failed nor re-reads what the holder's pull could not -- so it leaves the holder's message in place until the next sync starts, since every holder clears it on entry (#65); a write queued behind a sync that failed therefore leaves the label on `Sync error`, not `Synced`, until then. **The queue flags belong to the holder's user** (`_holderUserId`): `finishSync` drains them as the holder, and every push read and pull filter is `user_id = ?`-scoped, so a request for a _different_ user is never queued -- it waits for the release (`await _inFlight`, re-checking the lock each time round) and takes the lock itself, so the work runs for the user that asked (#63). The one place the two rules meet is the `MAX_QUEUED_DRAINS` cap above: a flag left set past it is drained by whichever holder comes next, and since #63 that may deterministically be the OTHER user, because a cross-user caller now waits for the release rather than queuing behind it. Still benign, and no different in kind from before -- a flag means no more than "re-read that user's pending rows" (and, for `_fullSyncQueued`, "pull them too"), so a drain for the wrong user only redoes that user's own push -- and, for a queued full sync, its pull -- redundant work, never wrong work, and the requester's rows stay pending for its next trigger. That is reachable on any account switch: `useSyncEngine` is keyed on the user id and its cleanup only flips `cancelled`, so the outgoing session keeps the lock while `startSyncSession` starts for the incoming one -- and the outgoing user's remaining work meets the new user's session (#111). Every follow-up its holder drains, a queued push carrying real pending rows included, is refused at its entry check; the push in flight still sends its remaining upserts, one request each, which the server refuses with `42501`, but stops before its next tombstone or split `DELETE`; and the pull in flight fails its read at the next empty page. Those rows stay pending for that user's next sign-in. `acquireLock` is synchronous and creates `_inFlight` as an unsettled deferred before the lock is observable -- a caller that finds the lock free is holding it by the time it yields, and a waiter never spins on a null or already-settled promise. A `deleted` row is pushed as a **tombstone**, not a hard delete: `update({ deleted_at })` filtered by `.is('deleted_at', null)` so a retry or a server-side cascade never re-stamps (and so never re-broadcasts) a row that is already dead. Zero matched rows is success — never pushed, already purged, or already tombstoned all mean "the server agrees it's gone" — and falls through to the local hard delete. That holds only for a push signed as the user: with no session, supabase-js signs every request with the anon key, a tombstone UPDATE then matches nothing whether or not the row is live, and the hard delete would silently undo the user's delete. So `pushChanges` refuses outright when `auth.getSession()` has no session to give, reports it through `setLastError` ("Couldn't renew your sign-in: …") and leaves every row queued (#95) -- and, since #111, when the session belongs to another user (an account switch mid-sync, whose token makes every tombstone of the outgoing user's rows match nothing), with a console warning only: the account signed in now has nothing to act on. A session can also go, or change hands, while a push runs, so every write whose zero-match answer the push acts on asks again just before it is sent (#111) -- each tombstone (per row, and per batch of transactions), which on a refusal stops sending tombstones and leaves the rest queued, and the split `DELETE` of a pending parent whose splits changed (with every local split `deleted`, no insert follows to be refused), which leaves that parent pending. These checks refuse first. Each is one session read -- per tombstone row, per transaction batch and per changed parent -- from storage on the happy path, the price `readAllPages` pays per empty page. What they leave is the window between a check and the request's own session read, when supabase-js signs it: two storage reads apart, milliseconds at most (Known Issues). A session lost after that check, mid-push, no longer undoes a delete either: since #109 the client refuses to send a PostgREST request signed with the anon key (see Paging), so that tombstone UPDATE fails like any failed write and the row stays `deleted` for the next push, whose entry check reports the sign-in. A session that passes to another user inside that window is not refused: that request is signed, so its zero match still undoes that one write. An upsert or a split insert the session may not make is refused with `42501` and needs no check of its own. `transaction_splits` has no tombstone of its own: splits ride their parent and stay hard-deleted. Locally a transaction's splits are hard-deleted BEFORE it, under its own condition, at each of the three places that hard-delete one (the tombstone consumer the pull, realtime and the reconcile share; the push's drop of a row whose upsert met a tombstone or a purge; the pushed delete), so an interruption between the two statements leaves a parent without its splits, which the next pull (at the latest the daily reconcile) or the next push deletes, never splits without a parent, which nothing would find again (#137). The tombstone consumer ends with a third statement: realtime runs it beside a sync holding the lock, and beside its own split refresh (#21), and a server split either of them writes between the two `DELETE`s, while the parent is still `synced`, is let in, so once the parent is gone the consumer deletes any split still pointing at it. The push's two pairs need none: the push holds the lock, and a server split is written only under a `synced` parent, by realtime's split refresh as well, while theirs are `pending` or `deleted`. At every launch `initDb` also deletes every `synced` split whose transaction row is gone (`sweepOrphanSyncedSplits`): what older builds left, and what can still be left by a storage failure that rolls back a transaction one of those statements joined, or by a kill just before the consumer's third statement. An unsynced one stays, since it looks exactly like what the reset's wipe keeps on purpose. The sweep is not a migration step, so no older build is locked out of the database. Deleting an account only tombstones the account; server triggers cascade the stamp to its transactions and rules (`005_tombstones.sql`), though the client still pushes child tombstones itself rather than depending on them. A child written into an account that was _already_ tombstoned is REJECTED by the server with `23503` rather than stamped dead, which is what keeps an offline-created row alive -- see the born-dead note in Known Issues. The push remembers such a row, and every other it can never upload as it is (a refusal of SQLSTATE class 22 or 23, or a rule it cannot prepare), under the user's `push_refusals:<user>` key; Settings counts them apart, naming their accounts, and lists them to move (a row whose account is gone), edit (a transaction refused for its date or amount while its account is here) or discard (#115). If a push fails because the server is missing `deleted_at` entirely, `pushChanges` reports it once through `setLastError` instead of retrying in silence.
- **Splits carry an `updated_at` (#20, `006_split_updated_at.sql`)** so the push can guard the write that marks them `'synced'` on the row it actually uploaded: it `.insert(...).select('id, updated_at')`, then per id runs `SET _sync_status = 'synced', updated_at = COALESCE(?, updated_at) WHERE id = ? AND updated_at IS ? AND _sync_status = 'pending'` -- the same guard the parent transaction has. A split edit that lands during the round trip replaces the splits under fresh ids, so every one of those statements matches nothing and the replacements stay `'pending'` for the next push, instead of being marked synced unsent and then overwritten by the pull's split refresh. That guard only holds because **the split refresh skips any parent whose LOCAL row is not `'synced'`**: our own push bumps the parent's server `updated_at`, so the next incremental pull lists it in `pulledTxnIds` even though its upsert was a guarded no-op, and refreshing splits there would insert the server's superseded copy (its id no longer exists locally) alongside the pending replacement -- which the next push then uploads together, turning a lost edit into a permanent duplicate. Since #125 the writes enforce that rule themselves: the local `DELETE` of a parent's synced splits and each split `INSERT` carry the same synced-parent condition inside the statement, so an edit that lands after a refresh checked the parent -- during its split read, or between two of its writes -- no longer gets the server's splits written beside its own: a re-split keeps only its own set, and a field edit leaves the parent's splits to be refreshed after its push, as described next. Nothing is given up, because **a pending parent's split set is replaced on the server only when one of its local splits is unsynced** (#97). An edit that touches the splits leaves such a row (`applyTransactionUpdate` marks the rows it replaces or removes `deleted` and inserts the new ones `pending`), and then the next push replaces the server's set with this device's anyway. A parent edited without touching its splits is uploaded alone and carries the server's set forward, and since that push bumps the parent's server `updated_at`, the pull after it refreshes the splits here. When the device clock runs ahead of the server's, that stamp can be no later than the pull cursor, so the pull would skip the parent: the push detects exactly that and reads the parent's splits itself, after its loop (#112; see the clock-skew bullet in Known Issues). The rule exists because this device's copy of an untouched set can be stale or missing. Another device may have re-split the parent, or the store may hold the parent without its splits: a download left it so (a split read that failed, or a bootstrap killed before it), or realtime delivered it before its splits (`applyTransactionEvent` writes the parent, and its splits follow through the split refresh its burst's split events start, a window and a read later; a lost event or a failed read leaves them to the next pull, #21; reachable today only through another device's transaction from a legacy recurring template that carries splits). Replacing the server's set from that copy deleted the other device's splits -- or, for a parent edited in the split-less state, every split it had, on every device. That push-side gap (#96 found the relaunch path into it) is what this guard closes; refreshing pending parents instead would bring the duplicate above back. `IS` rather than `=` because a local `updated_at` may be NULL (a split the local migration 2 could not backfill, or one pulled from a pre-006 server) and SQLite's `=` is not NULL-safe; for the same reason a NULL is sent as an **absent key** rather than an explicit null, so the server's `not null default now()` applies and the stamp comes back to heal the row. That omission is decided once per upload, never per row: when any split in the `.insert()` lacks a stamp, the key is left off every split in it, because postgrest-js (2.101.1) sends a bulk insert with `?columns=` set to the union of its rows' keys and PostgREST fills a listed key that a row omits with NULL, so a per-row omission beside a stamped sibling still arrives as an explicit null and the insert fails with `23502` -- not a missing-column error, so the push reports nothing, and the parent, whose server splits the `DELETE` just before the insert has already removed, stays `'pending'` and fails the same way on every push. Leaving the key off every row costs only a server restamp of the siblings that had one, which the read-back adopts; an upload is one parent's live splits today (one `.insert()` per pending parent), and batching the push (#29) would change what it covers.
- **`fullSync`**: Push then pull. If a sync **for the same user** is already in flight it queues a full sync and awaits the holder (which drains it before releasing) instead of silently returning, so `syncNow` and sign-out get the sync they asked for. If the holder is syncing someone else it waits for the lock and then runs its own push and pull (#63) -- `syncNow`/`promptSignOut` during an account switch therefore wait for the other user's sync rather than returning early with nothing done, and that sync, running on under the new user's session, is refused at its next session check rather than run under the new token (#111).
- **`initialPull`**: Bootstrap for first login -- pages every read to fetch all remote data (live rows only; tombstones are never downloaded), refuses before its first read without a session, or under another user's (#95, #111; every read would answer `[]` under the anon key, or under that user's RLS, and its stamps would declare the device fully pulled over nothing; since #109 an anon-signed read is refused before it is sent, see Paging, and this check is the second line, refusing first and in the sign-in's own words; under another user's session, whose reads are signed and sent, the wrapper is no second line there; `readAllPages`' third rule is, and this check still refuses first, reporting "Signed in as a different account" where that rule would fail the download as "initialPull accounts failed"), abandons the download on any failed read so the cursors stay unset, and sets all three meta keys **from a snapshot taken before the first remote read**, never from an end-of-pull `now` (a bootstrap of a large history spans many round trips, and stamping the later time declares that whole window pulled), including `last_txn_reconcile_at` so a fresh device does not immediately re-enumerate what it just downloaded. The loop is written for an **empty** store, and since #96 it only starts over one (the store is checked once, before the first read; a row written during the download is covered by the split loop itself since #113 -- it writes a parent's splits only while that parent is still synced, checked before the split read to bound it and, since #125, by each split `INSERT` itself, which closes the window in which a re-split got the server's splits beside its own -- so a parent the loop lands and the user re-splits keeps its own splits, and one edited without touching them, a status toggle say, is left pending with no splits here, or with a partial set when the edit lands inside the batch's writes, and pushed alone: the pull after that push refreshes its splits, or the push itself reads them when the stamp the parent adopts is no later than the pull cursor, as a device clock running ahead of the server's makes it (#112); nothing is deleted first, since over an empty store no stale synced split sits under a parent it downloads, which before #110 a wipe that collided with a hook's own transaction could leave behind, and since then only SQLite abandoning the wipe's transaction by itself on a storage failure (a full disk, an I/O error) can, see `resetLocalData`): a store that already holds any of this user's rows -- a first bootstrap killed mid-download (rows landed, no keys; probably the commonest way in); one that gave up on a failed read (a session lost mid-download included, #95) with no pull after it to record an attempt, because its session was cancelled before `startSyncSession`'s `fullSync`, or that `fullSync` was refused for want of a session (a refusal stamps neither key, #95), or its push threw before it reached the pull (as every push did over a malformed rule template until `pushTable` guarded its row transform, #129); a reset whose download threw after landing some tables; or a local write or realtime event that landed a row before the check (benign: the pull still completes over it) -- runs the `pullChanges` substitute described next instead, whose no-cursor read (tombstones included), reconcile and synced-parent split refresh cover what the loop lacks, with one gap, which #97's push-side guard closes: a parent that went pending before its splits landed has none locally and the refresh skips it. Its next push used to delete its server splits and upload none; since #97 it uploads such a parent alone, the server keeps its splits, and the pull after that push brings them down here (or, when a device clock running ahead of the server's would make that pull miss the parent, the push itself, #112). If a sync **for the same user** already holds the lock it queues a full sync instead and awaits it. That substitute is a `pullChanges` with unset cursors, and it is **not** an equivalent bootstrap: it also downloads every tombstoned transaction and runs the reconcile enumeration (which, for a user with no transactions, never banks its key and so repeats each sync until one exists), and where `initialPull` gives up on a failed read it swallows and reports the failure (#66) and still stamps `last_pull_attempt_at` (unless it was refused for want of a session, which stamps neither), so `needsInitialPull` turns false -- only `last_pull_at`, the "Last synced" line, waits for a pull that completes. It converges anyway, because with no cursor every read `pullChanges` swallows and reports is retried by the next sync (see the cursor rule under `pullChanges`), and no remote read is keyed on either pull key -- they only answer `needsInitialPull`, and `last_pull_at` feeds "Last synced" in Settings. `startSyncSession` runs that same pull straight after an `initialPull` that failed, so the startup sequence depends on the same rule. None of that reasoning survives a cross-user collision, so a bootstrap requested while **another user's** sync holds the lock does not queue: the drain would run as the holder, download nothing for the user who asked, and still leave `needsInitialPull` true with no error to show. It waits for the release and then runs the bootstrap itself, store check included (#63).
- **`pullChanges`**: Full-table pull for accounts/rules (`pullTableFull`) that reconciles deletions AND force-heals any `synced` row whose `updated_at` drifted from the server in either direction (`forceUpsertRemoteAccount`/`forceUpsertRemoteRule`, mirroring the transaction self-heal — relevant because `accounts.initial_balance` feeds every total). These tables stay full-table because they are tiny; the read partitions into live rows (which upsert as before) and tombstoned rows (which route to a scoped local delete). All three steps run on every pull whatever the others did, and `last_pull_at` -- the "Last synced" line in Settings -- is stamped only when every one of them read and applied everything (#66): a failed read, or an empty read that one of the #19 guards below refused to trust, withholds it, `pullChanges` resolves `false`, and the first such failure is reported through `setLastError`. A failed pull never unsets the key, so it keeps the time of the last complete pull. Every run that gets as far as its reads (one refused for want of a session stamps neither), complete or not, also stamps `last_pull_attempt_at` from the same instant, and `needsInitialPull` is true only while both keys are unset: an incomplete pull must not send the next launch back to `initialPull`, which is written for an empty store -- its split loop deletes no stale synced split, so it would insert the server's splits beside synced ones another device has since replaced (a pending replacement it has spared since #113), and it banks both transaction keys past any tombstone written in between. Since #96 `initialPull` itself takes that same route over a store that holds any of this user's rows. Under `throwOnError` the reads that already threw -- both whole-table reads, the incremental page, and the split reads for the parents it pulled -- still throw first and stamp neither key; a reconcile that could not complete never threw and still does not (see `resetLocalData`). **A pull with no session reads nothing (#95).** When `auth.getSession()` has no session to give, supabase-js discards its error and signs every request with the anon key, and RLS answers every read `[]` with no error at all -- which step 1 below takes for "nothing changed" (banking its cursor over a window it never read) and a new user's pull for complete. So `pullChanges` asks `getSession()` itself before any read, and with no session it is refused: it reports "Couldn't renew your sign-in: …" (the refresh's failure, mapped by `describeRequestError`) or "Couldn't verify your sign-in" (nothing stored), resolves `false` and stamps neither key -- nothing was read, as for a download that throws, so a fresh device still bootstraps on the next launch; under `throwOnError` it throws. A session that belongs to another user is refused the same way (#111) -- nothing read, neither key stamped -- but with a console warning only (thrown as "Signed in as a different account" under `throwOnError`): after an account switch, the outgoing user's pull is not the new account's to fix. The session can also go, or change hands, between two pages of one read, so `readAllPages` asks again on every empty page (see Paging). Since #109 an anon-signed read is refused before it is sent (see Paging), so these checks are the second line; they still refuse before any read, stamp neither key, and name the refresh's own failure. Under another user's session those reads are signed, and sent, so the wrapper is no second line there; `readAllPages`' third rule is, failing every read at its first empty page. Self-healing pull for transactions (`pullTransactions`) is two passes:
  1. **Incremental, every sync**: `updated_at > cursor`. Because a delete is now an ordinary `UPDATE` that stamps `deleted_at`, this pass sees deletions too — a tombstoned row routes to a scoped local delete (splits first) instead of an upsert, and never enters the pulled/touched sets. This is the whole point of tombstones: per-sync cost is proportional to what changed, not to total history.
  2. **Periodic reconcile, at most once per `RECONCILE_INTERVAL_MS` (24h)**, gated on the `last_txn_reconcile_at:${userId}` meta key. Enumerates all remote `(id, updated_at, deleted_at)` -- tombstones included, deliberately -- and treats a tombstoned row as absent. It counts RAW rows separately from live ones so "the server says everything is deleted" stays distinguishable from "the read returned nothing"; filtering server-side would collapse the two and the #19 guard would then refuse the honest answer forever. It -- via the pure `planTransactionReconcile` -- deletes server-removed rows, pulls rows missing locally, and force-refreshes (`forceUpsertRemoteTransaction`) any `synced` row whose timestamp differs in _either_ direction, reading each batch's parents and then their splits before writing either, so a failed read withholds the whole batch and the key (#62). It then writes one parent at a time: the parent's fields under a placeholder stamp (`''`), its splits replaced, and the server's stamp adopted last, so a stop anywhere in between (a kill, a statement that throws) leaves a drift the next pass re-plans, never a parent that matches the server over the wrong splits (#136). Realtime's last-write-wins guard refuses any row over the placeholder, so an event that lands inside a parent's writes is dropped, and the next due reconcile brings it; realtime's split refresh (#21) waits for the sync lock the reconcile runs under, so it cannot write inside that window either. No parent is inserted at its own turn: one the pass's snapshot held is written there only while it is still here, and every parent of the batch the device lacked is written first, at the placeholder over no splits (#151), so a tombstone that realtime applies before a parent's turn is not undone, except one for a lacked parent that lands before its early write (once the batch's parent read has served it: during the rest of that read, the split read, or while an earlier lacked parent is written first), which is still undone until a later pass reads it. A stop leaves each lacked parent that was written early and whose turn had not begun showing, with the server's fields and amount but none of its split rows, until the next pull's reconcile (no screen shows split lines yet, #26); one the early writes had not reached stays absent, as before. This is what lets a device recover from a server correction whose `updated_at` is _older_ than the device cursor (which the fast-path skips forever), and from a tombstone that was purged before the device ever pulled it. The key only advances after a pass actually completes — not on error, and not on the empty-enumeration skip — so a misconfigured RLS policy keeps retrying rather than going quiet for 24h. A push clears it before its own split refresh (#112) and puts it back only after a refresh that read everything, so a refresh that failed a read or stopped, even by a kill, leaves it cleared and the next pull runs the pass (#140; see the clock-skew bullet in Known Issues). **An empty remote read is never authoritative**: `planTransactionReconcile` returns no deletions unless the caller confirms the enumeration actually came back with rows (`remoteReadReturnedRows`), and `pullTableFull` mirrors that check on its own read, so a clean-but-empty response (a broken RLS policy, say -- the anon-key case is refused before the read and on every empty page since #95) can never wipe the local store. The cursor is subject to the same rule: `last_txn_pull_at` is only advanced when the incremental pass actually read -- every transaction page, and every split batch for the parents the pull touched -- since banking it over an unread window would hide those changes from `gt('updated_at', cursor)` permanently now that the reconcile is only a daily backstop. For splits even the backstop does not help: a parent upserted by that pull already matches the server, so the reconcile never refreshes it, and without the hold its splits stay missing until the parent is next edited. A parent the reconcile heals never depends on that cursor, and must not: no incremental read returns a row that is no newer than the cursor, however far back it is held. Its splits are read inside the reconcile instead, before the parent is written, so a failed read there leaves the parent stale and the reconcile key unbanked, and the next pass plans the same row again (#62) -- which is why only the incrementally pulled ids reach the split-refresh step.
- **Paging**: **Every remote read pages** -- `.order('id').range()` through the `readAllPages`/`readAll` helpers, advancing by the rows RETURNED and stopping only on an empty page -- because PostgREST clamps every response at `max_rows` (1000 on hosted Supabase) and says nothing about having done so (#64). Engine-wide, not a `pullChanges` detail: `initialPull`'s four reads, both `pullTableFull` tables, the incremental transaction pass, the reconcile enumeration and all three split reads. The only exception is `resetLocalData`'s single-row reachability probe, which asks for exactly one row and wants no more. A short page is precisely what the clamp looks like, so stopping on one -- or advancing by the page size that was ASKED for rather than the rows returned -- silently truncates the read, and a truncated read is not empty, so the #19 guard does not catch it. The cost is one trailing empty request per read or batch; the alternative was a read whose missing tail reads as "the server no longer has these rows", i.e. deletion authority over rows nobody ever saw. A third rule since #95: **an empty page ends a read only if the client could sign it.** Under the anon key RLS answers `200 []`, the same bytes as the end of the table, and a session can go between two pages of one read, so every empty page -- the first one included -- asks `auth.getSession()`, and with no session the read fails with its own error ("your sign-in could not be renewed (…)"), as it does under another user's session (#111: "your sign-in belongs to a different account" -- RLS answers this user's rows `[]` there too, so each read takes the user it is for, `{ userId }`): the pages already delivered stand, and every caller withholds what a failed read withholds (its cursor, its reconcile key, its absence-deletes). Never on a page that returned rows, which a signed request did. The cost is one session read per read-ending empty page, from storage on the happy path. The check cannot see which key signed the page itself, so a refresh that failed for the page and succeeded for the check used to get an anonymous `[]` trusted. Since #109 no such page is sent: `withAnonRestRejection` (`lib/fetchWithTimeout.ts`), the outermost `global.fetch` wrapper in `lib/supabase.ts`, refuses any `/rest/v1/` request whose `Authorization` is `Bearer <anon key>`, and postgrest-js resolves the refusal as `{ error }` ("NoSessionError: your sign-in could not be verified", which `describeRequestError` passes through without the name), so the read fails before the check is asked, and the check is the second line (Known Issues). A page signed as another user is sent and answered `[]`, and for it the check is the only line (#111).
- **`resetLocalData`**: Recovery escape hatch, surfaced in Settings as "Reset & re-download from cloud" for the rare case the local store drifts past what the reconcile can heal (e.g. an OPFS-backed SQLite file that "Clear site data" won't drop). Holds the `_syncInProgress` lock for the WHOLE operation and uses the lock-free `pushChanges`/`pullChanges` primitives (NOT `fullSync`/`initialPull`), so a background AppState/NetInfo sync can't slip between steps and either race the wipe or hold the lock when the re-bootstrap runs (which would make it a no-op, leaving the device wiped-but-empty). It refuses outright when the lock is held, whoever holds it, but it does record itself as the holder, so a request arriving for another user waits for it instead of being mis-queued into the reset's own drain (#63). Order: refuse without a session, or under another user's (#95, #111: with none, the push would be refused too, and the reachability probe below read `[]` under the anon key -- no error, so "reachable" -- until #109, which refuses that probe before it is sent: a session lost between this check and the probe now fails it as "Can't reach the cloud -- … (your sign-in could not be verified)"; another user's session answers this user's rows the same way, and its probe is signed, so sent, and "reachable" still; that refusal reads "Signed in as a different account — reset cancelled, your local data is unchanged."), flush pending edits up (and abort if any of the user's rows remain unsynced afterward, saying which of them no connection clears -- the rows the push was refused for good, to move, edit or discard in Settings (#115) -- so a swallowed push error isn't wiped away), confirm the cloud is reachable BEFORE wiping (an offline reset aborts without touching local data), check the session again as the last thing before the wipe (it can go, or pass to another user, during the push and the probe, and a wipe followed by a pull with no session downloads nothing into an empty device; the check stays outside any SQLite transaction, since inside the token's expiry margin it is a refresh of up to 30 s, and on web it can first wait up to 5 s for auth-js's cross-tab lock or queue behind a refresh already in flight), wipe the user's synced rows from every local table plus their five `sync_meta` keys (the four pull keys and the push's refusals; `wipeLocalData`, which first counts the user's unsynced rows again and refuses the same way, #97), then re-download via `pullChanges` in `throwOnError` mode — a failed download surfaces as a failed reset and leaves both pull keys unset (so `needsInitialPull` turns true → next-launch re-bootstrap -- over any rows the failed download landed, that runs `pullChanges`, not the bootstrap loop (#96) -- unless a pull runs first: a drained queued full sync or any later sync records an attempt if it gets as far as its reads (one refused for want of a session stamps neither), and the recovery is then a no-cursor `pullChanges`) rather than a silently partial cache. A failed read there throws and fails the reset as before; a failed reconcile enumeration or refresh batch after the wipe does not throw -- the reset resolves, the pull reports through `setLastError`, `last_pull_at` is withheld, and the next sync retries the reconcile (#66). **The guard and the wipe are both per-user (#87)**: `user_id = ?`, and splits (which have no `user_id`) through their parent. They are the two halves of one rule: the guard counts the user's pending and deleted rows and the wipe deletes only the user's synced ones (a split only when it and its parent are, #126), so a row that is unsynced when its table's `DELETE` runs is kept. A row whose `_sync_status` is `NULL` is neither counted nor wiped, and the re-download's guarded upserts skip it too, so a reset no longer heals such a row, which keeps whatever fields it drifted to; no writer produces one. Since #97 the guard and the wipe share one `countUnsyncedRows` and one refusal message (at the guard it also says which rows no connection clears, #115), and the wipe runs the count as the first statement of its own transaction: mutation hooks are not gated by the lock, and the probe's round trip (up to 30 s) and the second session check sit between the guard's count and the wipe, so a row written there used to be wiped unpushed. A refusal commits that transaction -- nothing of the wipe's is in it yet -- and throws afterwards. `withTransactionAsync` is `BEGIN`/`COMMIT` on the connection every hook shares, not an exclusive lock, so a hook's plain write (one made outside `withTransactionAsync`) that lands between the `BEGIN` and the count joins the transaction, and rolling back would discard the very row the count reported as kept. A hook's plain write that joins after the count is kept as well when its row is unsynced as its table's `DELETE` runs (#126), and the re-download upserts around it: a create's `INSERT` (a transaction, a rule) when it lands before the accounts `DELETE`, and an `UPDATE` of an existing row (`useUpdateAccount`, `useReceiptPhoto`, `useRemoveReceipt`, `useDeleteRecurringRule`) when it lands before its table's `DELETE`. A create checks its account inside its `INSERT` (#163), so one landing after the accounts `DELETE` -- or after the `COMMIT`, until the re-download writes the account back -- finds a synced account gone, writes nothing, and is refused with "This account no longer exists on this device, so … was not saved."; the user saves it again once the account is back. Before #163 it landed `pending` under the wiped account and the drain pushed it. Before #126 each was wiped unpushed when its table's `DELETE` had not run yet, and a recurring-rule delete landing there came back live from the re-download. Two orders remain. An `UPDATE` landing after its table's `DELETE` finds no row, as a hook queued behind the wipe does, and the re-download restores the server's copy. The writer then fails instead of reporting success: a rule delete with "This recurring rule no longer exists on this device…", after which the re-download brings the rule back live for the user to delete again, and a receipt attach with "The receipt was not attached…", after removing the file it had just uploaded (best effort: a removal Storage refuses is only warned about, and since #152 `009_receipt_storage_policies.sql` lets a user remove their own) (#138), and a receipt removal with "The receipt was removed, but this transaction no longer exists on this device, or was deleted here." (#23; when Storage found the photo already gone, "The receipt's photo was already gone, and this transaction no longer exists on this device, or was deleted here."); an account edit throws its own "no local row matched". Since #23 every upload has a key of its own, so the attach's removal takes only the file it uploaded; before, the upload overwrote the transaction's earlier receipt of the same extension in place, and the removal took the photo the row the re-download restores still named. A receipt removal has already removed its photo from Storage when its `UPDATE` matches nothing, so the row the re-download restores names a photo that is gone: the edit screen says the photo is missing, and removing the receipt again clears it, since Storage answers that second removal with nothing removed, which the hook takes for a photo already gone. The window itself is as it was before #126, which does not close it. A field edit landing between the split `DELETE` and the transactions `DELETE` (among the plain writes, only the receipt hooks edit a transaction: `useReceiptPhoto`'s attach and `useRemoveReceipt`'s removal) keeps its parent, pending, but not the parent's synced splits, which the split `DELETE` took while the parent was still synced; that loses nothing: the push uploads the parent alone, the server keeps its splits, and the pull after it (or #112's refresh in the push) brings them back. A realtime write is synced, so it is still wiped or kept by table order, and the re-download restores or refreshes it; realtime's split refresh (#21) writes nothing inside the wipe: it waits for the lock the reset holds. A hook with a transaction of its own (`transactionUpdate.ts`, `transferCreate.ts`, `transactionDelete.ts`, `accountDelete.ts`, `transactionImport.ts`, `usePostRecurringTransaction`, `useReorderAccounts`) never joins: since #110 every `withTransactionAsync` caller on the connection waits for the one before it (`lib/transactionQueue.ts`). Before that, its `BEGIN` failed inside the wipe's transaction and expo-sqlite's `ROLLBACK` ended the wipe early: the remaining `DELETE`s committed one at a time and the reset rejected with the raw "cannot rollback - no transaction is active", with the user's rows and keys all gone, or the parents gone and their splits left behind; the other way round, a wipe landing in a hook's transaction left a transfer delete with one leg deleted. Now arrival order decides. Only SQLite abandoning the wipe's transaction by itself on a storage failure (a full disk, an I/O error) can still split it: its later statements then commit alone, as they did in a collision. A hook that went first leaves its rows pending, and the wipe's count refuses over them. One that comes after runs over the emptied store: a delete or a reorder matches nothing and the re-download brings the row back for the user to repeat; an account delete matches nothing too, and the re-download restores the account and its children; an update's `UPDATE` matches no row and it refuses there, before any other write, so nothing of it commits and the mutation fails, its optimistic change undone (#127; before, a re-split's new split rows committed under no parent, and after the re-download the next push uploaded them beside the parent's old ones; since #139 that `UPDATE` also skips a row this device has marked `deleted` -- `_sync_status IS NOT 'deleted'`, NULL-safe -- and refuses it the same way, with "This transaction was deleted on this device, so this change was not saved.", where it used to set the row back to `pending` and the push uploaded the edit instead of the delete); a transfer or a CSV import into an account the wipe took (a synced one) refuses before writing anything, its account read being the first statement of its transaction (#163), and the re-download brings the account back for the user to try again -- before #163 it wrote pending rows into the emptied store, which the re-download upserted around and the reset's drain pushed, as it still does into a pending account, which the wipe keeps -- and a recurring post refuses with "This recurring rule no longer exists on this device…" before writing anything (#154), where it used to post and lose its advance, and the re-download brings the rule back due. Another account signed in on the same device is untouched: its unsynced rows neither block the reset nor appear in the refusal's count, and its rows, pending work and `sync_meta` keys stay exactly as they were, so it is not re-downloaded either. Both used to be device-wide, and while the wipe took every account's rows, refusing over anyone's pending rows was the conservative choice -- but it held one account's reset hostage to another's unsynced rows, which it can neither see nor push, and a reset that did run discarded the other account's cache.
- **Conflict resolution**: Last-write-wins, except that **delete wins over a concurrent edit**. Local `ON CONFLICT DO UPDATE ... WHERE _sync_status = 'synced'` protects unsynced local edits from being overwritten by remote data. The transaction reconcile treats the server as authoritative for already-`synced` rows, so it overwrites them regardless of timestamp order -- but still never touches `pending`/`deleted` rows. When a pending edit lands on a row another device tombstoned, the edit applies but the tombstone survives (PostgREST only sets the keys in the payload, and `deleted_at` is never one of them), so the push read-back sees `deleted_at` set and drops the row locally instead of marking it synced. The alternative -- edit wins -- resurrects a row the user already deleted, which is exactly what the old hard-delete push did. `purge_tombstones()` reclaims the tombstone 30 to 37 days after the delete (weekly, since `007`), but delete still wins after that (#98): the purge records the id of every account, transaction and rule it removes in `purged_ids` (`008_purged_ids.sql`), a `BEFORE INSERT` trigger refuses a re-insert of one with `23503` and `hint = 'purged'`, and the push treats that answer like a read-back tombstone (`isPurgedRowError`) and drops the row locally. The ids are kept for a year, and a row the server never held has a fresh id and is unaffected; see Known Issues for what remains.
- **Sync meta keys**: Scoped by userId (`last_pull_at:${userId}`, `last_pull_attempt_at:${userId}`, `last_txn_pull_at:${userId}`, `last_txn_reconcile_at:${userId}`) to support multi-user sign-in on the same device. `wipeLocalData` clears the four pull keys, so a reset forces a fresh reconcile for that user, and a push whose split refresh failed a read or stopped clears that user's `last_txn_reconcile_at` alone, so the next pull reconciles (#140). `last_pull_at` is stamped only by a pull that read and trusted every table, and a pull that could not leaves it as it was, so "Last synced" is the time of the last COMPLETE pull; `last_pull_attempt_at` is stamped by every `pullChanges` that gets as far as its reads (one refused for want of a session stamps neither), complete or not, and `needsInitialPull` is true only while both are unset (#66). `push_refusals:${userId}` holds the rows the last pushes were refused for good (JSON: table, id, the `updated_at` refused, account, kind, code, the account's name, first seen), rewritten by a push whose answers change it; an entry counts only while its row is still pending at that `updated_at`; the wipe clears it with the four (#115).

### Sync Orchestration (`lib/query.tsx`)

- `useSyncEngine` hook runs inside `SyncProvider` (nested inside `AuthProvider`) and calls `startSyncSession` from `lib/sync.ts`: open the DB, `initialPull` if this device has never pulled, then one `fullSync`.
- Keyed on the user **id**, not the `User` object: auth-js emits a fresh object on every auth event, and keying on it tore the engine down mid-bootstrap on nearly every launch (#55). The effect's `cancelled` flag stops the follow-up sync and cache invalidations after sign-out or unmount, but not a sync that already holds the lock: on an account switch that one runs on under the new user's session, and the engine refuses what is left of it (#111).
- Triggers: app foreground (`AppState`), network reconnection (`NetInfo`) -- both only once the bootstrap has finished -- and initial login. Outside this hook, realtime's channel runs a `fullSync` when it comes back after an error or a timeout (`lib/hooks/useRealtimeSync.ts`, #21; not before this device's first download).
- The `QueryClient` has `MutationCache`/`QueryCache` `onError` handlers: a failed mutation is logged with its key (and, in development only, its variables, which carry amounts, payees and memos) and surfaced through `setLastError` (the label shows `Sync error`), since the mutation hooks have no `onError` of their own and `Alert.alert` is a no-op on web; `useReceiptPhoto`, which is not a mutation, reports a failed upload or a refused attach through the same `setLastError` by hand, as "Save failed: …" (#138); `useRemoveReceipt` is a mutation, so a failed or refused removal arrives through the cache, and the edit screen also shows it inline (#23); a failed query is only logged, with its key. The sync engine reports through the same `setLastError`: a sync, bootstrap or reset that failed, a server missing a migration this build needs (`pushChanges`), a pull that could not read or trust every table (#66), a push, pull, bootstrap or reset refused because the client had no session to sign its requests with ("Couldn't renew your sign-in: …", #95), and a bootstrap or reset refused because the session belongs to another account ("Signed in as a different account", #111; a push or pull refused that way only warns in the console). While the device is offline, the label and the Settings status line say `Offline` ahead of any recorded error (#66): a foreground sync runs whatever the connectivity, so the error is then almost always the offline itself, and the reconnection sync clears it before its next attempt.
- The cache is the signed-in account's (#177). No query key names the user (`['accounts']`, `['transaction', id]`, ...), and a result stays fresh for 30 s and in memory for 5 min, so the `AuthProvider` (`lib/auth.tsx`) removes every query -- not the mutations, which are the previous account's edits waiting for the network -- whenever the account it hands the screens changes: after a sign-out, and after a sign-in straight over another account (on web the sign-in screen is reachable by its URL while signed in, and auth-js reports that sign-in as `SIGNED_IN` alone; on every platform it follows a sign-out whose request failed, which leaves the session stored). It does so before the new session reaches a screen, which used to be handed the previous account's accounts, register and transaction out of the cache, without a read. The provider removes at mount and on every change, its first session included: the client outlives the provider, which the root layout's `ErrorBoundary` mounts again on Retry over the same cache, whose account it cannot know, and the screens it renders while it loads, before any session, would otherwise be handed what that cache holds; at launch there is nothing to remove. The kept receipt URLs go at the same moment (`forgetReceiptUrls`). Component state is not the cache: the tabs are keyed by the account (`app/(tabs)/_layout.tsx`), so a change of account that never passes through "signed out" mounts them afresh, where the Accounts tab's Edit Account sheet used to stay open on the previous account's account. It reads the client through `useQueryClient`, so the `AuthProvider` sits inside the `QueryProvider` (`app/_layout.tsx`).

### Data Tables

`accounts`, `transactions`, `transaction_splits`, `recurring_rules` -- all have `_sync_status` (`synced` | `pending` | `deleted`). The `sync_meta` table stores pull timestamps and the push's refusals (#115). Receipt photos live in the private Storage bucket `receipts`, one folder per user: `<user id>/<transaction id>.<upload id>.<ext>`, one key per upload since #23, so an upload never lands on an object a transaction names (a key from before, `<user id>/<transaction id>.<ext>`, stays valid wherever a transaction names it), the extension and content type taken from the picked asset's `mimeType`, else from a known image extension of its file name or of its URI's last path segment (`lib/receiptObject.ts`, #152), never from the raw text after the URI's last dot, which on web is inside a `blob:` URL; `transactions.receipt_path` holds the key, and `009_receipt_storage_policies.sql` lets each user read, write, overwrite and remove only the objects directly in their own folder, so an upload from a build before #152 on web or in the desktop app, whose key carries the tail of the `blob:` URL, is refused. A stored receipt is shown through a signed URL (`lib/receiptStorage.ts`, #23): an hour's token, kept per key for the account that signed it and handed out again, to that account only, while it has more than ten minutes left, so the refetch every sync ends with does not download the photo again. A change of account drops every kept URL -- a sign-out, or a sign-in straight over another account, which auth-js reports as `SIGNED_IN` alone -- and a signing still out at that moment keeps none; the query is keyed by account, so TanStack's cache never hands one account's URL to another. Sign-out wipes no local rows, so the previous account's transactions stay on the device; no screen shows the next account one of them since #177 (Conventions, **Reads are the signed-in user's**), and a key outside the user's folder is still refused before any request, as the second line: the screen says "This receipt belongs to a different account." and offers neither Retry nor Remove (`receiptStorage.test.ts`, `useReceiptUrl.test.ts`). The URL goes to the image component and nowhere else, never into a message or a log line (React Native's Image reports a failed load as "Failed to load <URL>" on iOS and react-native-web's in like words, which the screens never read); the platforms' HTTP caches keep it beside the photo's bytes, as for any image, its token expired within the hour. The registers mark a transaction that has a receipt with a paperclip and sign nothing. Removing a receipt (`useRemoveReceipt`) removes its photo from Storage first and then clears `receipt_path` (`lib/receiptRemove.ts`), which the push uploads as null like any field edit; a removal that fails changes nothing, and one of a key outside the user's folder (another account's transaction, which no screen reaches since #177) is refused before any request, since Storage would answer it with nothing removed, which reads as a photo already gone (`useRemoveReceipt.test.ts`). Replacing one leaves the replaced photo in the bucket, named by nothing: the push uploads the whole row, so another device's edit of the transaction, made before it pulled the replace, still names the old key and its push puts that key back on the server, where its photo must still be (`syncReceiptReplace.test.ts`). The weekly receipt sweep (#176) removes such a photo only once no transaction has named it for 30 days and its own transaction has not changed for as long, so the stale push finds it still there unless it comes more than 30 days after the replace (`syncReceiptSweep.test.ts`; Known Issues). Such an edit undoes a removal the same way, and the transaction then names a photo that is gone, which the edit screen shows as missing until the receipt is removed again. And a removal made on a device that had not yet pulled another device's replace pushes null over that replace, as any conflicting edit is resolved by arrival, and the replacing photo is then named by nothing. Deleting a transaction or its account removes no photo at once: the sweep removes it once the purge has reclaimed the transaction (Known Issues).

### Desktop shell (Electron)

`electron/src/main.ts` is the macOS entry point. It boots an in-process loopback HTTP server (`server.ts`, fixed port 49217 with ephemeral fallback) over `dist/` and points a `BrowserWindow` at it. This preserves absolute asset URLs from `expo export -p web` and gives the renderer a stable origin so `localStorage` (Supabase session, AsyncStorage) persists across launches. The service worker is intentionally suppressed in Electron via a `navigator.userAgent` check in `app/+html.tsx`.

`preload.ts` exposes a deliberately narrow `window.electronAPI` via `contextBridge`: `saveCsv` (round-trips through `ipc.ts`'s `csv:save` handler, which validates `event.senderFrame` origin before showing the save dialog) and `onExportCsv` (menu→renderer event). The menu listener is mounted in `app/(tabs)/_layout.tsx` so `Cmd+E` works from any tab, calling the shared `lib/exportTransactions.ts` helper. Renderer navigation is locked to the local origin in `main.ts` (off-origin links go to `shell.openExternal`).

When adding desktop-only behavior: extend the existing `window.electronAPI` surface rather than enabling `nodeIntegration`. When adding Expo-side code that touches browser-only globals, gate on `Platform.OS === 'web'` (Electron presents as web to React Native) and use `electronAPI` for desktop-specific paths.

## 2. Conventions

- **Style**: PascalCase for components, camelCase for variables/functions, 2-space indent.
- **Naming**: Hook files are `useX.ts`, mapper functions in `lib/mappers.ts`, types in `lib/types.ts`.
- **Reads are the signed-in user's**: several accounts sign in on one device in turn and sign-out wipes no local rows (only a reset wipes, and only its own user's), so every read a screen makes filters `user_id = ?`, by id and by account id included (`useTransaction`, `useAccount`, `useTransactions`; splits through their parent), and another account's row reads as missing (#177): the edit screen, which offers its form only over a row it has loaded, shows #127's "This transaction no longer exists on this device. It may have been deleted elsewhere or by a reset." in its place, and the register its gone banner (#163) and none of that account's rows. A writer that files a row under an account requires the account to be the user's own as well as live (`LIVE_ACCOUNT` and `readAccountRefusal` in `lib/accountWriteGuard.ts`, and the recurring post's own read; since 010 the server refuses a row filed under another user's account too, for the builds without this check, #189), and words another account's as missing, never as "was deleted on this device"; so does `useUpdateAccount`, whose account the Edit Account sheet and icon picker hold in their own state. The other writers that change a row by id (`applyTransactionUpdate`, `applyTransactionDelete`, the receipt writers, `applyAccountDelete`, the rule delete and the post's rule advance) do not look at the user: each is reached only from a screen that loaded the row through the signed-in user's read and offers it only while that read holds it -- the cache is emptied and the tabs mounted afresh when the account changes -- and a new screen that offers one must load its row first and never keep it in its own state. Most query keys do not name the user (**Query keys** below): the `AuthProvider` empties the cache when the account changes (Sync Orchestration). The sync status is one store every account shares (`lib/syncStatus.ts`), so it says whose counts, refused rows and "Last synced" it holds (`snapshotUserId`, written with them by `refreshSyncState`, their only writer), and `useSyncStatus` hands them only to that user, reading the signed-in user's back when another account's land (#115, #193).
- **Soft-delete pattern**: All deletions set `_sync_status = 'deleted'` and `updated_at = now`. Queries filter with `AND _sync_status != 'deleted'`. Push writes a server-side tombstone (`deleted_at`) rather than deleting the remote row, then hard-deletes locally -- the local hard delete is scoped `AND _sync_status = 'deleted'` so it cannot swallow an edit made while the push was in flight. Splits follow their parent: a `deleted` split is never tombstoned, but left out of the push's upload (whose remote delete-then-insert drops it) and hard-deleted locally once its parent is marked synced (#97). The app marks splits `deleted` -- with their transaction, or when an edit replaces or removes them -- and never hard-deletes one itself; the push retires them. A splits UI (#26) must mark a removed split `deleted` the same way: a parent whose splits are all `synced` is uploaded alone, so a split the UI simply dropped would stay on the server. There is deliberately **no local `deleted_at` column**: the tombstone exists only on the server, and consuming one means hard-deleting the local row (`lib/tombstones.ts`). Local deletes of remote data are always scoped to `_sync_status = 'synced'`, so an incoming tombstone can never discard a `pending` edit or a queued local delete.
- **Archived accounts**: `accounts.is_archived` is the reversible, non-destructive exit; delete stays the destructive one. An archived account is hidden from the accounts list and its total, the desktop sidebar's list, every account picker (transfer, recurring rule, CSV import) and the **All Accounts** ledger and its balance summary (`allAccountsLedger` in `lib/register.ts`). It is deliberately still counted in Reports and in CSV export -- history stays meaningful and a backup stays complete. Its register keeps working but is read-mostly: a banner with Unarchive, no add-transaction or transfer button (not even while the account loads), existing transactions still editable; a New Transaction screen that still names it -- opened before another device archived it, or by a stale link -- refuses to save (`useCreateTransaction`: "This account is archived, so the transaction was not saved.", #76). Recurring rules on an archived account stay in place; Post Now is hidden for them, and `usePostRecurringTransaction` refuses to post into one. Unarchive from the collapsed **Archived** group on the Accounts tab or from that banner; the desktop sidebar's **Archived** group opens by itself while an archived account's register is open. A new read site that lists accounts should filter `!a.isArchived` unless it is a history or export view. Its card in the **Archived** group shows **Excluded** under a dimmed balance whatever its own **Include in Net Balance** switch says; the switch keeps its value and applies again after Unarchive (#146). The Accounts tab's and the sidebar's totals, that label and the All Accounts register's summary read one predicate, `isExcludedFromTotals` in `lib/accountTotals.ts`, and a new total over accounts should sum through `netBalance` there. The register lists the transactions of an active account whose switch is off but sums only the accounts the predicate counts, so its Balance is the All Accounts total it opens from (#76; it used to count the switched-off accounts too).
- **Mutation pattern**: Write to SQLite -> call `requestPush(user!.id)` -> invalidate relevant query keys in `onSuccess` (in `onSettled` where a refusal leaves a stale list on screen: `useUpdateTransaction`, `useDeleteRecurringRule`, `useUpdateAccount`, `usePostRecurringTransaction`, `useCreateTransaction`, `useCreateTransfer`, `useCreateRecurringRule`, `useRemoveReceipt`, `useMoveRefusedRow`, `useDiscardRefusedRow`). A write that touches more than one row goes in one `withTransactionAsync` (`transactionUpdate.ts`, `transferCreate.ts`, `transactionDelete.ts`, `accountDelete.ts`, `transactionImport.ts`, `usePostRecurringTransaction`, `useReorderAccounts`), so an interruption cannot leave half of it behind: `useDeleteTransaction` used to mark the splits and then the parent as separate statements, and an interruption in between left `deleted` splits under a live parent that no push could clear (#97). That holds for a crash or a failed statement, and since #110 for another transaction on the shared connection too: every `withTransactionAsync` caller waits for the one before it (`lib/transactionQueue.ts`, installed by `getDb()`), where a colliding one used to end this one early and let its later statements commit alone. So a hook's transaction and the reset's wipe run one after the other (see `resetLocalData` above). A writer whose `UPDATE` must find its row checks the statement's `changes`, and when it matched nothing, returns from the task and throws only once `withTransactionAsync` has resolved, so the transaction commits whatever plain write joined it. A throw inside the task would roll that back: a pull's write, which the pull then banks its cursor past, or, for `applyTransactionUpdate` (#127), the tombstone `DELETE`s that made the row vanish, bringing back a transaction deleted elsewhere. The wipe's refusal has the same shape (#97). A writer whose `UPDATE` sets an existing row `pending` also skips a row this device has marked `deleted` -- `AND _sync_status IS NOT 'deleted'`, NULL-safe -- and refuses in its own words, since setting it back to `pending` would make the push upload the edit instead of the delete: `applyTransactionUpdate` (#139), the receipt attach (#138), the receipt removal (#23) and `useUpdateAccount` (#153: "This account was deleted on this device, so this change was not saved."; before, an edit that reached the account before the push had uploaded its delete -- from a list that had not refetched, or a register re-opened on it (the browser's Forward, a stale link) while the push was in flight or failing -- brought the account back live while its children were tombstoned; once uploaded, the push has removed the row and the edit is refused with #55's "no local row matched"). The move of a row the push can never upload (`lib/refusedRowActions.ts`, #115) is the only writer of `account_id`: one statement, taking the row only while it is still `pending` at the version the push was refused, into a live account of the user's, and never a transfer into its other side's account. The reorder needs no filter: it writes only the rows its own read, inside its serialised transaction, found live. The recurring post's rule advance takes the filter too, and goes first in its transaction, so a refused post writes nothing: it used to post from a rule deleted here and bring the rule back, and after an account delete post into the deleted account, where the server refuses the new row (#154). A post of an occurrence already posted here resolves without writing. `useDeleteRecurringRule` and `usePostRecurringTransaction` share a TanStack `scope`, so offline taps on rules resume one at a time in the order they were made. A writer that creates a row under an account refuses an account this device has deleted or no longer holds (#163, `lib/accountWriteGuard.ts`; live is `_sync_status IS NOT 'deleted'`, NULL-safe): the server refuses a new child of a tombstoned account with `23503` (005's `inherit_account_tombstone`), and such a row used to stay `pending` here forever, shown in no register and counted by the reset guard -- a register re-opened on a deleted account (the browser's Forward, a stale link), or on screen when another device deleted it, still offered "+" and its transfer button. The two single-row creates, `useCreateTransaction` and `useCreateRecurringRule`, carry the check inside their `INSERT` (`INSERT … SELECT … WHERE EXISTS (…)`), so nothing can land between the check and the write and they open no transaction: a zero match throws at once, and a status read only picks the words ("This account was deleted on this device, so the transaction was not saved.", or "…no longer exists on this device…" for a missing one). Such an `INSERT` is still a plain statement, which the queue does not hold back, so it can land inside `applyAccountDelete`'s transaction, between its statements: that is why the delete marks the account first and its children after (#163), so a create landing before the account's mark is a child the marks then take, and one landing after it is refused -- marked last, the account still looked live to a create landing after the children's marks, which then stayed `pending` under it. The multi-row writers, `createTransfer` and the CSV import's `applyTransactionImport` (one transaction for the batch, all rows or none), read the accounts as the first statement of their transaction and return-then-throw, and the transfer names the dead account by its role, the from account first, each in its own case ("The account you are transferring from was deleted on this device, so the transfer was not saved."), since the refused transfer's refetch takes the dead account off the form; the recurring post's account check words the same two cases ("…, so nothing was posted."). None of them can know of an account another device has deleted whose tombstone this device has not pulled yet (Known Issues). Never call `withTransactionAsync` inside another one's task: the inner call would wait for the outer and the outer for it, so every later transaction waits forever, and every later plain write stays uncommitted (visible to the app's own reads) until the process dies, all without an error (the file's docblock lists the nine callers; none nests).
- **Seeding a form from a query**: seed once per loaded row **id**, not on every refetch. A screen's query is refetched by ordinary sync activity -- the realtime echo of this device's own push (`lib/hooks/useRealtimeSync.ts`) and the blanket `queryClient.invalidateQueries()` that every sync ends with (`lib/query.tsx`) -- and a push adopts the server's `updated_at`, so the refetched object is a new reference even when nothing the user cares about changed. An effect keyed on that object re-seeds the form mid-edit and discards whatever has been typed (#85). Guard it with a `useRef` holding the id already seeded; the only screen that needs this today is `app/transaction/[id].tsx`.
- **Dates**: a stored date (a transaction's `txn_date`, a rule's `next_date`) is a day of the calendar written `YYYY-MM-DD`, not an instant. Every form checks its date before it saves, with `isDateStr` (`lib/format.ts`, #192): that shape, and a day of the calendar by `calendarDate`, the one calendar rule, which the CSV import reads with too. The date field of the web and desktop forms (`components/WebDateInput.tsx`, an `<input type="date">`) reads `''` once it is emptied and while a date is only partly typed; the New Transaction, Edit Transaction, Transfer and New Recurring forms then say "Please enter a valid date." above their button (`DATE_MISSING_MESSAGE`), where they used to save it: the register showed the row as "Invalid Date", the server refused it (22007) so it stayed pending, and a rule's blank next date failed every Post Now ("Invalid time value"). The date pickers read one with `parseDateStr`, the start of that day here, and store a choice with `formatDateStr`, the local day of a `Date`; `todayString` is `formatDateStr(new Date())` (`lib/format.ts`; each of the four form screens had its own copy of the pair until #36). Never `new Date('2026-01-15')` or `toISOString()` for a stored date: both read UTC, so in New York the first is the evening of the 14th and the second gives tomorrow's date from 8 pm (7 pm in winter) (three places still do: `advanceDate` in `lib/hooks/useRecurringRules.ts`, the recurring list's due check and the Reports period). The CSV import reads its date column with `parseImportDate` (`lib/csvImport.ts`, #36): month first (`4/2/2026`, or `04/02/26` with the server's reading of a two-digit year) or year first (`2026-04-02`), any time of day after it dropped, and only a day of the calendar. Its dedup (`applyTransactionImport`) still tells two lines of one day apart by the date as written, and each stored row covers one line, so a payment app's two fares of one day are not one. Any other date is not imported, and the preview lists the line with the reason, as it lists a misread amount (both reasons at once when both fail). Day first is never inferred: `15/01/2026` is refused ("can only be day first"), since the same file's `05/01/2026` reads as May 1 without a word, and the preview then warns that a day-first file's dates up to the 12th were read the wrong way round. The import used to store a date it could not read as written (`15/01/2026` as `2026-15-01`), which the server refuses (22008), so the row stayed pending forever.
- **Typed amounts**: text a person types as an amount -- the New Account starting balance, a recurring rule's amount -- is read with `parseAmount` (`lib/format.ts`), which reads the whole en-US text (`-68,655.02`, `$1,234.56`, `-$5`) or returns `null`; never `parseFloat`, which stops at the first character it cannot read and turned `-68,655.02` into `-68` (#145). The CSV import reads its amount column with `parseImportAmount` (`lib/csvImport.ts`): `parseAmount`, plus the accounting negative `(5.00)` that bank and spreadsheet exports write, with zeros past the cents dropped (`$123.4500` is $123.45; any other digit there, as in `1.005`, is refused). A line whose amount is missing or in any other form is not imported, and the preview lists it with its line number and the reason, above the rows it will import (a line of fewer than two fields, or one with nothing in any field such as a spreadsheet's empty `,,,,` row, is skipped as before); the strip before `parseFloat` it replaces read `(5.00)` as +5 and `12,34` as 1234, and imported fourteen-digit amounts the push could never send (#165). The starting balance goes through `parseStartingBalance`, which keeps a blank field at 0, the placeholder's 0.00. A refused amount is reported in the form itself, as every validation is (**Form errors** below): under the New Account modal's title and above the recurring screen's Create Rule button. The transaction and transfer amount fields are cents entry (`sanitizeCentsInput` in `lib/register.ts`): every non-digit is dropped and the field shows the amount as it is typed, so a separator cannot cut one short; every digit after the twelfth is dropped too, the most `numeric(12,2)` holds, so no amount the server would refuse can be typed or pasted (#165). The edit screen seeds its field from the stored row, so its Save also refuses an amount beyond that (`centsInputToAmount`), above the Save button, rather than queue again a row saved before the cap, one the server refused.
- **Form errors**: a form reports what the person must fix in the form itself, on every platform, with `components/FormError.tsx` -- never through `Alert.alert` alone, which is a no-op on web and in Electron (react-native-web's `Alert` is an empty class), so the transaction, transfer, CSV import and Edit Account forms used to say nothing there (#164). Place the line where it stays in view when it appears: under a bottom sheet's title (New Account, Edit Account), which stays above the iOS keyboard (the keyboard covers the New Account sheet from below, and the Edit Account sheet rises above it: **The iOS keyboard**, below), and directly above the submit button of a form that scrolls (the transaction, transfer, import and recurring screens; on the import preview, inside its floating footer above the buttons). Give it a screen-prefixed `testID` (`new-txn-error`). A failure of the form's own submit goes there too (`Transfer failed: ...`, `Import failed: ...`); a failed mutation also reaches the sync indicator through the mutation cache, as before. Screen readers hear it: `FormError` keeps a polite live region (`aria-live`, which react-native-web renders as the DOM attribute and React Native maps to Android's `accessibilityLiveRegion`) mounted while its message comes and goes, since a region mounted together with its text is not reliably announced, and on iOS, which has no live regions, `focusFormError` (`lib/formError.ts`) asks VoiceOver to move to each new message half a second after it appears (a queued announcement alone was not heard, #178), and announces it only when the line cannot be found; the same message set again is not read again. The request is the layout-changed notification with the line as the element to move to, a path traced in React Native's source; that VoiceOver then moves there and reads the line is not yet confirmed on a device. A result outside a form (a failed CSV export) uses `window.alert` on web, as the reset does. A confirmation (a delete, the reset, a rule's Post, the sign-out) asks through `confirm` (`lib/confirm.ts`, #37): `window.confirm` with the message alone on web and in Electron, where the e2e specs answer the browser's dialog, and elsewhere a native alert with Cancel first and the confirming button last (red when it destroys something); the sign-out with changes waiting keeps its own per-platform flow (`lib/promptSignOut.ts` says why). Act on the answer as every call site does, `const ok = await confirm({ … }); if (ok) { … }`, and never in an early return on `!ok`: with the `await` forgotten, `tsc` refuses `if (ok)` (TS2801, a truth test on the bare promise, unless the block reads `ok`) but compiles `if (!ok) return` and `if (!confirm({ … })) return`, which then run the action without waiting for the answer -- on iOS while the alert is still up, on web and in Electron whatever the person chose.
- **The iOS keyboard**: a form stays usable with the iOS keyboard up -- the field being typed into in view, and the submit button within reach (#39). A form that scrolls sets `automaticallyAdjustKeyboardInsets` on its `ScrollView` (the transaction, transfer, import and recurring screens): iOS insets the content by what the keyboard covers, measured on screen, and scrolls the focused field above it; web and Android ignore the prop. Keep `keyboardShouldPersistTaps="handled"` beside it, so the first tap on the button reaches the button while the keyboard is up. On the transfer, import and recurring screens a drag then scrolls the form to its button with the keyboard still up. The two transaction screens also set `keyboardDismissMode="on-drag"`, so there a drag puts the keyboard away and Save is reached after it, as before #39: what the prop gives them is the focused field above the keyboard, where the new-transaction screen's memo used to sit partly or wholly under it. Keep that `on-drag`: the number pad has no key that puts it away (a tap on an empty part of the form also does). Those screens are page-sheet modals under a native header (`presentation: 'modal'` in `app/_layout.tsx`), and there a `KeyboardAvoidingView` falls short: it compares its own frame, which is relative to its parent, with the keyboard's position on screen, so it misses the sheet's top inset and the header -- 132 pt on an iPhone 17 Pro and 100 pt on an iPhone SE in the iOS 26.5 simulator (measured for #39, which replaced the transaction screens' own `KeyboardAvoidingView`). Use a `KeyboardAvoidingView` only where its frame is its place on screen: a `Modal`'s full-window overlay (the Edit Account sheet, which rises above the keyboard whole) and the sign-in and sign-up screens, which have no header. Never both on one form: the content is then pushed up twice, leaving a blank gap above the keyboard (measured). The New Account sheet keeps its text fields at its top instead (#164).
- **Query keys**: `['accounts']`, `['transactions', accountId]`, `['transactions', '__all__']`, `['recurring_rules']`, `['transaction', id]`, `['account', id]`, `['reports', userId, period]`.
- **Header buttons**: Use plain `paddingLeft: 16` or `paddingRight: 16` -- no `height: '100%'` (causes misalignment on iOS due to safe area insets).
- **testIDs**: Every interactive element should have a `testID` prop, prefixed by screen name to avoid collisions in Expo Router's Stack (e.g. `sign-in-email`, `sign-up-email`). These become `data-testid` on web and `id` on native.
- **Accessibility labels**: a control whose only content is an icon carries `accessibilityRole` and an `accessibilityLabel` that says what it does (`New transaction`, `Discard picked photo`), never what the icon is; a `testID` is not a label. A label that depends on state follows it (`Collapse sidebar` / `Expand sidebar`), and a control that also shows a state says the state, then what pressing does (the sync dot: `Synced, sync now`). A checkbox's label is what checking it means, and `aria-checked` says whether it is: on web the register's cleared box is `Cleared` in both states, as a label that followed the state would read a pending row as "Pending, not checked". On iOS the box is not reached on its own, because a row reads its children's labels as its own, without their checked state, and the row opens the transaction; there its label is the transaction's state (`Pending` / `Cleared`), from `lib/clearedBoxLabel.ts`. react-native-web renders `accessibilityRole="button"` as a `<button>` element and the label as `aria-label`. `lib/__tests__/iconButtonLabels.test.ts` fails on a pressable with no `Text` inside it that lacks a label or a role (an empty label, and a role of `none`, count as none); a control that is icon-only some of the time (the collapsed sidebar) is labelled by hand. A status line that appears on its own goes through `FormError` for its live region (#38): the receipt line on the transaction screens, the register's gone banner, and the edit screen's gone line, whose region is mounted with the spinner it replaces and which stays through a refetch (#195): TanStack clears the error of a query without data each time it fetches again, so a line read from the error alone went away with every sync's refetch and came back, read out again on web and with a new VoiceOver move on iOS (`useTransactionGone` keeps the not-found while the refetch runs); the receipt line passes `moveFocus={false}`, so VoiceOver reads it without being moved to it, away from the field the person is on.

| Layer      | Tool             | Location                  | Command              |
| ---------- | ---------------- | ------------------------- | -------------------- |
| Unit       | Jest + jest-expo | `lib/__tests__/*.test.ts` | `npm test`           |

Config files: `jest.config.js`, `playwright.config.ts`. Full E2E setup docs: [`e2e/README.md`](./e2e/README.md).

### Unit tests (Jest)

Existing test files cover pure functions: `format.test.ts`, `mappers.test.ts`, `csvImport.test.ts`, `register.test.ts`, `syncStatusHelpers.test.ts`.

Tests go in `lib/__tests__/`. Jest is configured with `jest-expo` preset and `@/` path alias. The `testPathIgnorePatterns` in `jest.config.js` excludes `e2e/` so Playwright `.spec.ts` files are not picked up.

### E2E web tests (Playwright)

Playwright runs against the Expo web build (Chromium desktop + WebKit mobile emulation). The config auto-starts Metro on port 8081. Specs go in `e2e/web/*.spec.ts`.

**Authentication**: A `globalSetup` script (`e2e/web/global-setup.ts`) signs in via the UI using credentials from `.env.e2e`, dismisses onboarding, and saves the session to `e2e/web/.auth/user.json`. Authenticated specs load this via `storageState`. Unauthenticated specs (`smoke.spec.ts`, `auth.spec.ts`) run in a separate project.

Key patterns:

- Use `getByTestId` with screen-prefixed IDs (e.g. `sign-in-email`) since Expo Router's Stack keeps multiple screens in the DOM simultaneously on web.
- For back-navigation tests where the Stack pushes a new screen instead of popping, use `.last()` to target the topmost instance.
- Use `getByText` and `getByRole` for assertions that don't need testIDs, but beware of duplicate text across stacked screens.
- Each authenticated spec should clean up after itself (delete created accounts/transactions) so the test user stays clean. Deletes are local-first -- the mutation soft-deletes in SQLite and fires `requestPush()` without awaiting it -- so a spec that returns on the Delete click closes the browser context before the tombstone reaches Supabase. End with `deleteAccountAndWaitForPush` from `e2e/web/helpers/test-accounts.ts`, which waits for the card to leave the list and then for the sidebar label to read exactly `Synced`. The engine refreshes the pending count before it clears the syncing flag, so once a write's `requestPush` has been called (which the mutation does synchronously, before the list re-renders) that word cannot appear again until the push has completed. `expectSynced` alone is only meaningful after such a re-render, never straight after a click.
- Before typing after a react-native-web `Modal` closes (into a second modal, or a field on the screen behind it), wait for the closing modal to detach with `waitForModalToClose(page, <testID inside it>)` from `e2e/web/helpers/test-accounts.ts`. The closing modal stays mounted and keeps its document-level focus trap active for its 250 ms slide-out, so a `fill()` in that window types into the closing modal instead (issue #55). Waiting for `hidden` is not enough; after a `fill()` that matters, assert `toHaveValue` before saving.
- Before the startup sync begins, Settings already looks settled (the sidebar reads `Synced` and the `settings-reset-local` row is enabled) and only "Last synced: Never" shows otherwise, so a guard on the reset row must wait for "Last synced" to leave "Never" before it checks `aria-disabled` (see `settings.spec.ts`).
- Debris from failed attempts is handled in CI: with `E2E_PURGE_STALE_TEST_ACCOUNTS=1` (set in `test.yml`), `global-setup.ts` tombstones test-prefixed accounts older than 30 minutes through the REST API before signing in. Since #123 the repository's Playwright jobs run one at a time (a repository-wide `concurrency` group on the `e2e-web` job in `test.yml`; a second job waits as pending), so in CI the age gate is belt and braces; it still matters for a local run next to a CI job. Locally the purge is opt-in; `cleanup-test-accounts.spec.ts` remains the browser-driven purge of everything.

### E2E mobile tests (Maestro)

Maestro flows go in `e2e/mobile/flows/*.yaml`. Each flow declares `appId: app.nestworth.ios` and uses `id:` selectors matching the `testID` props. Metro must be running in a separate terminal since the dev client loads JS over the network.

**Authentication**: `npm run e2e:mobile` reads `E2E_TEST_EMAIL` and `E2E_TEST_PASSWORD` from `.env.e2e` and passes them to Maestro.

### What to add when making changes

**For every new feature:**

1. Add a unit test in `lib/__tests__/` for any new pure logic (formatters, parsers, helpers, mappers).
2. Add `testID` props to new interactive elements, prefixed by screen name.
3. No new Playwright spec or Maestro flow by default: Playwright is a small smoke layer run in single passes, and a new spec needs the owner's explicit ask.

**For every bug fix:**

1. Add a unit test that reproduces the bug and verifies the fix (regression test). Sync-engine regressions go against `lib/testing/syncFixture.ts` and must be proven to fail without the fix.
2. If the bug is UI-visible, verify the fix in a browser or on a device and state what was verified in the PR body.

PRs touching `lib/sync.ts` get an independent review pass before merge.

**Running all checks before committing:**

```bash
npm run typecheck && npm run lint && npm run format:check && npm test && npm run e2e:web
```

CI runs the same gates on every PR (`.github/workflows/test.yml`): typecheck, lint,
format check, unit tests, a web bundle export, and an Electron main compile.
`migrate.yml` applies one Supabase migration file and runs only when a person starts it
from the Actions tab on `main`: its secret belongs to the `migrate` environment, whose
one deployment rule is `main` (#190). So a migration is merged and applied ahead of the
client -- in a pull request of its own when the client depends on it -- an order
Netlify's push-triggered web deploy cannot otherwise guarantee. Releases take two more:
`release.yml`, started by a person (or by `npm run release`), bumps the version on a
`release/X.Y.Z` branch for its pull request; `publish-release.yml` follows every Tests
run on `main` and, for a green (squash-merged) release commit, tags it, dispatches
`testflight.yml` (the EAS build and TestFlight submission, which can also be started by
hand) for the tag, creates the GitHub Release, and deletes the merged release branch.
The release decisions and the workflows' steps live in `scripts/release/` (the npm
wrappers in `scripts/release*.js`), unit-tested with a recording fake for git, gh and
npm in `lib/__tests__/release*.test.ts`. The README's Releasing section has the flow and
its TestFlight section the one-time setup. The
Playwright job additionally needs `E2E_TEST_EMAIL`, `E2E_TEST_PASSWORD`,
`EXPO_PUBLIC_SUPABASE_URL`, and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (or the legacy

**Lint severity:** the React Compiler rule family (`react-hooks/set-state-in-effect`,
`static-components`, `refs`, `immutability`, `preserve-manual-memoization`) is set to
`warn` in `eslint.config.js` rather than `error`. Those warnings mark genuine

**Local database backups live outside the repo,** at `~/nestworth-backups`. They
contain real account and transaction data, so they are deliberately kept out of the

## 4. Known Issues & Gotchas

- **Deploys are forward-only once a new migration ships.** `runMigrations` refuses to
  open a database whose `user_version` is newer than the running build
  (`lib/migrations.ts`) — correct, since the older code would write rows against a
  schema it does not understand. The consequence is operational: rolling the web
  deploy back across a migration makes every returning browser hit that guard,
  because the OPFS database is not rolled back with the bundle. Roll forward instead.
  Local migration 2 (`split_updated_at`, #20) is the first one to make this real:
  before it, every shipped build was on version 1, so no rollback could trip the
  guard. Once it ships, rolling the web deploy -- or the Electron app -- back to
  1.1.2 leaves it unable to open its database until it is upgraded again, and on
  web the OPFS database is shared per origin, so it is not per-tab recoverable.
- **Clock skew can briefly defer the _periodic_ reconcile for rows this device just
  pushed.** Since push adopts the server's `updated_at`, a synced row carries SERVER
  time while the pull's `pullStartedAt` snapshot is CLIENT time. If the client clock is
  behind by δ, a row this device pushed looks "created mid-pull" for up to δ and is
  excluded from the reconcile pass, so a remote deletion of it is skipped until the
  clock catches up. This now only affects the 24h reconcile, not routine deletes: a
  tombstone arrives through the incremental pass as an explicit per-id assertion and
  needs no `pullStartedAt` comparison at all. Self-corrects; the durable fix is a local
  monotonic marker instead of comparing server-stamped timestamps against the client
  clock.
  The opposite skew had a cost that did not self-correct (#97); #112 fixed it. A
  pending transaction whose splits this device did not change is pushed alone and
  adopts the server's `updated_at`. If the client clock runs ahead of the server's by
  more than the time since the previous pull began, that stamp is no later than the
  cursor (the previous pull's start, in client time), so the next incremental pull
  would not list the transaction, and the daily reconcile would find the local and
  server stamps equal: a stale or missing local copy of its splits -- another
  device's re-split (#26), a download that failed, a transaction realtime delivered
  alone -- stayed until the transaction next changed on the server. The push now
  detects exactly that case, comparing the stamp with `last_txn_pull_at` in SQLite
  (`julianday`; a stamp equal to the cursor counts, since the pull's `>` excludes
  it), and reads those transactions' splits right after its loop, 200 ids per
  request. Under clocks in step it reads nothing, except for a transaction it
  inserts that was created before the previous pull began: that one keeps its own
  creation stamp, and the read finds no splits for it. Each of those transactions
  stays pending through that read; then it is marked synced with its own stamp, its
  splits are replaced, and it takes the server's stamp only after them (#128). So
  after a failed read, or a push interrupted after that mark (a kill, a statement that
  throws), the transaction is not left pending -- its edit is already on the server,
  and uploading it again could only overwrite a change another device made since --
  but synced WITHOUT the server's stamp, over its old splits, part of the new ones or
  none: the reconcile sees the drift and heals the transaction and its splits
  together at the next pull, because the push clears the user's reconcile key before
  that read and puts it back only after a refresh that read everything (#140;
  cleared first, since a killed push runs nothing after the statement it stopped
  at). That pull follows in the same sync when the read failed inside `fullSync`; a
  push that threw skips its sync's pull, and `requestPush` never pulls, so there it
  is the next sync's. Until then its splits may still be stale, and an edit another
  device makes to it within the skew is refused by the pull's last-write-wins guard
  (this device's stamp is ahead) until that reconcile force-heals it. One case stays
  unhealed: the realtime echo of its own upload can reach it after the mark, for an
  edit made longer than the skew before its push, and give it the server's stamp;
  then the stale splits stay until the transaction next changes on the server. A
  push interrupted before the mark leaves the transaction pending for its next push,
  which uploads it again: marked synced any earlier, the realtime echo of its own
  upload could give it the server's stamp before its splits were written.
- **A second browser tab can lose the migration write lock.** Two tabs opening the same
  OPFS database can race; the loser gets `database is locked`. `getDb()` drops a rejected
  init promise so the next call retries rather than poisoning the session (`lib/db.ts`).
- **Transaction split sync is delete-then-reinsert**: For a pending transaction that carries an unsynced split row, the push deletes all remote splits for it, then reinserts the live local ones; one whose splits are all `synced` (or that has none) is uploaded alone and keeps the server's splits (#97). This is not atomic -- if the process is interrupted between delete and insert, remote splits are lost (mitigated by keeping local copies as `'pending'` on failure). A _failed_ split upload also leaves the parent transaction `'pending'`, so a server missing `006_split_updated_at.sql` stops every transaction whose splits this device changed from syncing, not just its splits (since #97 one whose splits are untouched goes up alone) -- which is why `pushChanges` reports that case through `setLastError` (see `isMissingColumnError`) instead of retrying in silence. A failed read of the splits of a parent uploaded alone, when the pull after it would miss that parent (#112; the clock-skew bullet above), does not leave the parent `'pending'`, and neither does a push interrupted while it writes them (#128): the parent is marked synced with its own stamp and takes the server's only after its splits are written, so the reconcile heals it and its splits together at the next pull (the push clears the reconcile key before that read, #140). Splits are uploaded only for a `pending` parent, so a `pending` or `deleted` split under a `synced` parent is sent by no ordinary push. Three things leave one: a `useDeleteTransaction` interrupted between its two writes (before #97 made them one transaction); a split written after a concurrent push has read its parent's splits; and, latent until a splits UI (#26), an `applyTransactionUpdate` whose transaction ends early, after its parent write, rolling the parent back while its split writes commit alone -- the adoption heals the splits, and the rolled-back field changes are lost. Before #110 a collision with another transaction on the shared connection did that; now that transactions take turns (`lib/transactionQueue.ts`), only SQLite abandoning the transaction by itself on a storage failure (a full disk, an I/O error) can. Before #97 nothing cleared such a split, and the reset guard counted it forever ("Couldn't upload N unsynced change(s)" on every try). The push now adopts such a parent first: it marks it `pending` and re-uploads the whole set. A `deleted` split is left out of the upload and hard-deleted locally once its parent is marked synced; before #97 it was uploaded as a live row and stayed `deleted` locally forever. The adoption is last-write-wins on a parent this device did not edit: the re-upload overwrites any change to that parent that this device has not yet applied, exactly as the push of any `pending` parent does. It is confined to parents in that state, and a parent deleted elsewhere stays deleted while its tombstone lasts (the upsert lands on it and the read-back drops the parent). It stays deleted once `purge_tombstones` has reclaimed the tombstone too (#98): `008_purged_ids.sql` refuses to re-insert the purged id, and the push drops the adopted parent and its splits the same way (`isPurgedRowError`). Without that the adoption would re-insert the row, as any edit pushed after the purge did (a path that needs an orphaned split on a device that has not synced for the whole 30 to 37 days). The same refusal closes the second post-purge path, which #97's split guard opened: a plain field edit pushed after the purge would re-insert the transaction without its splits, since it goes up alone and the next pull then drops the local copies of the splits, where the push used to re-upload them. That edit is now refused and dropped as well. Both hold within the limits the retention bullet below lists.
- **Tombstone retention must stay far longer than the reconcile interval.**
  `purge_tombstones()` defaults to 30 days against a `RECONCILE_INTERVAL_MS` of 24h. The
  tombstone is the only _incremental_ signal that a row is gone, so purging one before
  every device has pulled it leaves those devices showing the row until their next
  periodic reconcile. Shortening retention towards 24h removes that margin. The function
  is `security definer` with EXECUTE revoked from `public`, `anon`, and `authenticated`,
  so no app session can call it. `007_schedule_purge_tombstones.sql` runs it weekly with
  `pg_cron` -- job `purge-tombstones`, Sundays 04:00 UTC, default retention, as the
  `postgres` role that scheduled it. The cadence only decides how long past the
  retention a tombstone lingers (up to a week), never how early it goes. Delete still wins
  over a concurrent edit once a tombstone is purged (`008_purged_ids.sql`, #98): the
  function records the id of every account, transaction and rule it removes -- the
  children its account delete cascades out included, though not the splits, which ride
  their parent -- in `purged_ids` before deleting it, and trims records older than a year
  in the same run. A `BEFORE INSERT` trigger on each of the three tables refuses a
  recorded id with `23503` and `hint = 'purged'`, and the push drops such a row locally,
  splits included, under the same guard as a read-back tombstone (`isPurgedRowError`).
  What remains: an edit pushed more than a year after the purge re-inserts the row, as
  hard deletes did (the push upserts on `id`, and the local row has no `deleted_at`); an
  id purged before 008 was applied was never recorded; a push that races the purge's own
  transaction can put a row back live with its id recorded, after which every edit to it
  is refused and dropped (008's header, item 5, has the mechanism and the remedy); and a
  row created offline under an account that has since been purged has a fresh id, so it
  meets the foreign key instead -- see the born-dead bullet below.
  `cron.job_run_details` records whether each run succeeded, not the three counts the
  function returns; to see those, run it by hand with
  `select * from public.purge_tombstones();` in the SQL editor as `postgres` -- which
  deletes remote data. The migration's header shows how to inspect or unschedule the job.
- **Split corrections that don't bump the parent `updated_at` won't refresh**: split sync piggybacks on the parent transaction landing in the pulled/refreshed set. `transaction_splits` gained an `updated_at` of its own in #20, but it is **not** a pull cursor -- splits are still fetched by `transaction_id` for the parents a pull touched, and they still have no tombstone. Editing splits through the app always bumps the parent, so this only affects out-of-band/server-side split edits. (Split refresh fetches the remote copy _before_ deleting the local one, so a failed fetch never drops local splits.)
- **`006_split_updated_at.sql` must land before the client that uses it, for the
  same reason.** The new client sends `updated_at` in its split INSERT and
  selects it back; against the old schema PostgREST rejects both with
  PGRST204/42703, the split upload fails, and that leaves the parent transaction
  `'pending'` as well -- so one missing column on a child table stops every
  transaction whose splits the device changed from syncing (since #97 one whose
  splits are untouched goes up without a split upload). While that lasts, the
  push's remote split DELETE succeeds before its INSERT fails, so every push wipes
  the server-side splits of every such transaction -- self-healing once 006 lands,
  because the local rows stay unsynced and the next push reinserts them, but a
  real reason not to leave the client out in front. (Historical: 006 was applied
  on 2026-09-16.) The reverse order is safe: an old client
  omits the column on insert and takes the `default now()`, and its `select *`
  pulls ignore a column it does not map. Run `migrate.yml` with the file first,
  then merge the client.
- **Supabase migrations are ordered and `005_tombstones.sql` must land before the
  client that uses it.** Against the old schema the new client's tombstone-filtered
  reads bail out safely, but its tombstone write fails outright and local deletes queue
  up forever. The reverse order is safe: an old client on the new schema keeps
  hard-deleting (which new clients notice via the periodic reconcile), it just keeps
  showing rows other devices tombstoned until it is upgraded. Push-side and pull-side
  tombstone support are also not independently deployable — push-only turns deletes into
  rows that never disappear, pull-only propagates them only every 24h — so they ship
  together.
- **Delete wins over a concurrent edit, and the edit is discarded silently.** If device B
  edits a transaction offline while device A deletes it, B's push applies the edit to the
  tombstoned server row but the tombstone survives, so B's read-back drops the row
  locally. B's edit is gone with no prompt. This is deliberate -- the alternative
  resurrects a row the user deliberately deleted -- but it is a real data-loss surface if
  the two devices are both in active use, and there is no UI telling B what happened.
  It holds after the tombstone is purged too: 008's guard refuses the re-insert with a
  hinted `23503`, and B drops the row locally then as well, with no prompt (the retention
  bullet above has the limits).
- **An emptied-_and-purged_ account needs "Reset & re-download".** Deleting every
  transaction is handled normally: the tombstones come back in the enumeration, so the
  reconcile sees rows and honours the all-deleted answer. The gap is narrower -- only once
  those tombstones have been PURGED does the enumeration genuinely return zero rows, and
  then the #19 guard declines to act on it because it is indistinguishable from a broken
  RLS policy. This is the intended trade (a latent whole-store wipe is far worse than a
  rare manual reset), and Settings → "Reset & re-download from cloud" is the recovery
  path.
- **A PostgREST request signed with the anon key is refused before it is sent
  (#109).** The session checks (#95) keep an anonymous `[]` from being read as the end
  of a table, but they cannot see which key signed a request. When the refresh a page's
  own request needed failed retryably (a 502/503/504, a network error), supabase-js
  signed that page with the anon key and RLS answered `[]`; if the check's own refresh
  then succeeded, the empty page was trusted. In step 3's split refresh that dropped the
  parent's local synced splits and reported the pull complete, cursor banked; the
  reconcile's split refresh did the same and banked its key; and a flapped page in a
  multi-page reconcile enumeration truncated it, absence-deleting the rows past it
  locally until the next reconcile. A session lost between a push's entry check and its
  tombstone UPDATE lost that delete the same way: under the anon key the UPDATE matched
  nothing, which is the success case that hard-deletes the local row, and the next
  signed pull brought the row back. Since #109 the outermost `global.fetch` wrapper in
  `lib/supabase.ts` (`withAnonRestRejection`, `lib/fetchWithTimeout.ts`) refuses any
  `/rest/v1/` request that is not signed as a user -- whose `Authorization` is not
  `Bearer <a token other than the anon key>`: `Bearer <anon key>`, how supabase-js signs
  with no session, and since #191 a missing or empty `Authorization` too, how newer
  supabase-js versions send a publishable key -- without sending it: supabase-js sets its
  headers before the wrapper sees the request, the app makes no intentional anonymous
  PostgREST call, and postgrest-js turns the refusal into `{ error }`, so the read or write fails and every existing failure path
  applies -- no absence-delete, no cursor or key banked, the row left `deleted` for the
  next push. `/auth/v1/*` (sign-in, sign-up and the token refresh, which auth-js signs
  with the anon key itself) and Storage are exempt by path. Since #191 "the anon key",
  here and throughout this file, is the key the client is built with: Supabase's
  publishable key (`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`) where the build has one, else
  the legacy anon key (`EXPO_PUBLIC_SUPABASE_ANON_KEY`), which Supabase retires by the
  end of 2026 (`lib/supabaseKey.ts`). The server answers both as the `anon` role, and
  `lib/supabase.ts` hands the wrapper the same constant it hands `createClient`, so the
  refusal follows whichever key the build signs with. The engine's own session
  checks stay as the second line: they refuse before any request is made, and they name
  the refresh's own failure ("Couldn't renew your sign-in: <cause>") where a refused
  request can only say "your sign-in could not be verified". A page whose own refresh
  STALLED is not refused as anon-signed: postgrest-js's 30 s timeout has fired by the
  time it arrives, and the wrapper rejects a request whose signal has already aborted
  the way fetch does, unsent, so it still reads "the request timed out" (an entry check
  that meets the stall says "Couldn't renew your sign-in: the request timed out"). A
  reset whose session is lost between its first check and its probe is now refused at
  the probe, as "Can't reach the cloud -- … (your sign-in could not be verified)".
  Requests signed with a user's own token go out as before, whatever the server makes
  of that token: one it rejects is answered 401, an error every path already handles.
- **An account switch mid-sync leaves two small residues (#111).** The outgoing user's
  remaining work is refused under the incoming user's session, by the engine's checks or
  by the server's `42501`, but the refused holder still ends in `finishSync`, which
  publishes the OUTGOING user's pending count, refused rows and "Last synced" into the
  status store. So does a stale `requestPush` for that user -- a mutation hook that
  captured the old id. Since #193 the store says whose numbers it holds (`snapshotUserId`)
  and `useSyncStatus` shows them to that user only: for the account signed in they read as
  nothing for one render while the hook reads that account's own back, never as the other
  account's (they did until the signed-in account's own sync ended, since #63). What stays
  shared is the device's: the stale `requestPush` still clears `lastError` as it takes the
  lock, and the outgoing sync's spinner shows until it releases the lock, which the
  incoming account's own sync waits for anyway; nothing is written or lost. And each check
  sits just before its write, not inside it. A session that changes hands in the
  window between the check and the request's own session read (when supabase-js signs
  it: two storage reads apart, milliseconds at most) still sends that one write, signed
  by the new user, and its zero match is taken for success while the server copy stays as
  it was. For an account or a rule that is one queued delete lost; for transactions one
  check guards a whole batch, so up to 200. A pending parent's split `DELETE` is exposed
  only when every local split under it is `deleted`, so that no insert follows to be
  refused: the parent is then marked synced and its removed splits are dropped. A session
  that goes in that window is refused since #109: that request would be anon-signed, so
  it fails and the row stays queued. The switch is not: its request is signed, just by
  the wrong user, and nothing but the check can tell.
- **A row created offline for an account another device deleted never syncs.** The
  server rejects it with `23503` (`inherit_account_tombstone`), exactly as the foreign key
  did before tombstones existed, so the row stays `pending` on the device and is retried on
  every push, forever. That is deliberate: the alternative -- stamping it dead -- makes the
  push read the tombstone back and hard-delete data the server has never held, destroying
  what the user typed. The push remembers such a row (#115): Settings counts it apart
  ("N change(s) can't be uploaded") and lists it under "Review changes that can't be
  uploaded", where it can be moved to a live account (the only writer of `account_id`;
  a transfer's leg moves alone, its link kept) or discarded (marked deleted: its
  tombstone matches nothing on the server and the push removes it here, its split lines
  first), and the reset's refusal says so instead of "Check your connection". Once the
  account's tombstone is pulled the row is in no register (Reports still counts it):
  that list is the only place it shows. Since #163 this device no longer
  writes such a row into an account it has deleted itself, or that a pulled tombstone
  has removed here: the writers refuse it (see Mutation pattern), and the register says
  the account is gone instead of offering "+" and its transfer button (at once when it
  is re-opened, and when another device's delete arrives by realtime). What remains is
  an account deleted elsewhere whose tombstone has not removed it here yet -- not pulled,
  or pulled while the account carried an edit this device had not pushed, which keeps
  the row until that push meets the tombstone -- a tombstone pulled between a transfer's,
  an import's or a post's account read and its writes, a stale live realtime event
  that puts back an account this device deleted until its tombstone's own event or the
  next pull removes it again, and the rows written before
  #163. The same hint-less `23503` is what a
  child of a deleted-_and-purged_ account gets -- since the account row is gone, from the
  foreign key, and since 010 from the check below, which comes first -- and it is left
  alone for the same reason: only a row whose own id was purged (`hint = 'purged'`, #98)
  is dropped. Since 010 (#189) the server also refuses a transaction or rule filed under
  an account that is not the row's user's -- the row #177's guard stops on every current
  build, written by an older one (a web tab open since before 1.4.0, a TestFlight or
  desktop build not yet upgraded) -- with that same hint-less `23503`
  (`reject_cross_user_account()`: "account <id> is not this user's"), so it is listed and
  moved the same way (Settings words its account as deleted: it is not one of the user's).
  Before 010 the server stored such a row, and the account's owner deleting the account
  took it with them: 005's cascade runs under that owner's row-level security and never
  sees it, so it stayed live under the dead account until the weekly purge adopted it
  (a tombstone its owner's devices then pulled) and deleted the account, whose foreign
  key cascade took it.
- **A receipt's photo outlives its transaction, for a while (#23's residue,
  swept since #176).** Deleting a transaction, or the account it belongs to,
  marks the rows deleted; the push tombstones them and `purge_tombstones`
  deletes them 30 to 37 days later. Nothing in the app removes the photo from
  the `receipts` bucket: neither the sync engine nor any migration touches
  Storage, and a removal made at delete time could not cover a delete made
  offline, on another device or by an older build. The same is left by every
  replace (the replaced photo is kept on purpose: another device's stale edit
  can name it again, see Data Tables), by an upload whose answer was lost or
  whose attach never reached the server, by a removal made on a device that had
  not yet pulled another device's replace (its null wins by arrival and leaves
  the replacing photo behind), and by an older build replacing a receipt. The
  weekly receipt sweep (`.github/workflows/sweep-receipts.yml` running
  `scripts/sweep-receipts.js` with a secret key, #176) removes them through the
  Storage API: every photo that no transaction, live or deleted, names, whose
  bytes are 30 days old, and whose own transaction (the id in its key,
  `<user id>/<transaction id>.`) has not changed for 30 days or is gone. A
  photo's own age is not enough: a replaced photo is old when it is replaced,
  and a stale edit names it again (`scripts/receipt-sweep/rule.js` says why
  the transaction's `updated_at` bounds the last time the server named it). So
  a deleted transaction's photo goes at the first sweep after the purge, and a
  replaced one 30 days after its transaction last changed. The bound: a removed
  photo is named again only by a push whose copy of the transaction last
  matched the server more than 30 days before (a device offline that long with
  an edit, or an edit the server kept refusing that long), or by a stale edit
  of a transaction deleted outside the purge (by a build from before
  tombstones, #47, which hard-deletes, or by hand), which re-inserts the row;
  every device then shows it missing, and removing it again clears it
  (`syncReceiptSweep.test.ts` pins the first). A removal is permanent: the
  bucket keeps no versions and Supabase's backups do not include Storage
  objects. The reverse happens too: a receipt removed on
  one device comes back, naming a photo that is gone, when another device pushes
  an edit of the transaction made before it pulled the removal; every device
  then shows it missing, and removing it again clears it. And Remove pressed on
  a screen not yet refreshed after another device's replace was pulled (the
  store already names the new photo, the screen still the old one) removes the
  replaced photo, kept for such a stale edit, from Storage and then clears
  nothing, without a word; the refresh that follows shows the new receipt, and
  an edit that names the removed photo again shows it missing, as above.
- **`deleted_at` is stamped by the server, never by the client.** A
  `normalize_deleted_at` trigger rewrites it to `now()` on the NULL → non-NULL transition
  on all three tables. Trusting the client clock would make the purge retention
  meaningless, since `purge_tombstones` compares against server `now()` -- the same reason
  `001` refuses to trust the client for `updated_at`.
- **A live child can still be born under a dead parent, and only the purge cleans it
  up.** `inherit_account_tombstone` deliberately takes no row lock on the parent (a
  `for share` there would deadlock against `accounts_tombstone_children`), so a child
  committed in the instant before the parent's tombstone becomes visible is born live.
  `purge_tombstones` adopts any such orphan before reclaiming anything. The client's
  periodic reconcile does NOT cover this: it only deletes local rows _absent_ from the
  enumeration, and a live orphan is present.
- **Migrations 001–004 cannot be replayed, and nothing applies a migration on push.**
  The first four were run by hand, and 001 creates its row-level-security policies with
  no existence guard (Postgres has no `create policy if not exists`), so `migrate.yml`
  refuses them. From 005 on every migration must be safe to run twice -- `if not exists`
  on columns and indexes, `drop trigger if exists` before `create trigger`,
  `drop policy if exists` before `create policy`, `create or replace` for functions -- and must be valid inside one transaction, which
  rules out `create index concurrently`. Nor may it make an older build's ordinary write
  fail with SQLSTATE class 22 or 23 (a `not null` column with no default, a `check` that
  values an older build writes break). Such a row used to wait, pending, for the app to
  update; since #115 the push takes the refusal for a permanent one, and Settings lists
  the row as one that can't be uploaded and offers Discard, which deletes it everywhere
  when the server held an earlier version. A refusal that is the point -- 010's, of a row
  filed under another user's account, which no current build writes -- raises `23503`
  with no hint, which Settings lists with Move as well (`refusalKind` in
  `lib/syncRefusals.ts`): never another class-23 code (Discard alone) and never
  `hint = 'purged'` (the row is dropped). Netlify builds the web client from its own git
  hook the instant `main` changes, so an automatic migration step could land after the
  client that needs it; run the migration workflow first, then let the client out.
- **iOS and macOS ship under different identifiers, deliberately.** iOS is
  `app.nestworth.ios` (`app.json`) and the Electron app is `com.nestworth.app`
  (`electron-builder.yml`). `com.nestworth.app` is registered to an Apple account
  that is not this team, and Apple's App ID namespace is global, so it can never be
  claimed here — the Developer portal refuses it outright. Local device builds
  worked for a long time regardless, because Xcode signed them with the team's
  wildcard App ID (`*`), which matches any bundle identifier; only App Store
  distribution needs an explicit registration, which is where it surfaced. The
  Electron identifier is untouched because Developer ID signing needs no App ID
  registration, and changing it would drop the desktop app's stored Supabase
  session. Keep the Maestro `appId` in `e2e/mobile/**` in step with the iOS value.
- **`expo-sqlite` web support**: Uses wa-sqlite (WASM) in a web worker, over an OPFS file (the AccessHandlePool VFS). Data durability on web is less guaranteed than native SQLite -- browser storage can be evicted. The OPFS-backed DB also survives DevTools "Clear site data" in Chromium, so a corrupted local store must be reset via Settings → "Reset & re-download from cloud" (`resetLocalData`) or by deleting the app's storage directory.
- **Expo Router Stack on web**: `<Link>` pushes new screens rather than replacing, so the DOM accumulates stacked screens. Tests must account for duplicate elements. Maestro on native does not have this issue since the Stack only renders the topmost screen.
- **Expo dev server `Cannot pipe to a closed or destroyed stream`**: Benign race condition in `expo-server` when Playwright disconnects before the response stream finishes. Does not affect test results.
- **Realtime (#21)** (`lib/hooks/useRealtimeSync.ts`): one channel per subscription, under a topic of its own (`db-changes-<n>`), with four listeners -- `accounts`, `transactions` and `recurring_rules` filtered on the user, `transaction_splits` unfiltered (the table has no `user_id`). A topic of its own because realtime-js hands back the channel already holding a topic and the socket routes every message by topic: under one fixed name, a sign-in straight over another account subscribed in the old topic, and what the server still sent the old account reached every listener of the new one (a binding matches any change until its join is answered), which wrote a rule as a transaction and a transaction as a rule. Each row event is written as it arrives, through the pull's own guarded upserts and `synced`-scoped deletes (`lib/realtimeHandlers.ts`), so an unsynced local row is never overwritten or deleted. A split event only names its parent, and the parent's whole set is read again from the server once the burst is over and written as the pull writes it (`refreshSplitsFromServer`): the user's `synced` parents only, never one at the reconcile's placeholder, every statement written only while the parent keeps the stamp it had before the read (a parent that moved on is read again, up to three such reads), and nothing at all when the set is already this device's (the echo of its own push). It never reads for, nor writes beside, a sync: it waits until no sync holds the lock before each read, and reads again a parent whose read a sync began during (a read not among those three, and ten at most), because every other writer of synced splits (the pull's step 3, the reconcile, the refresh after a push, the first download, the reset) runs under the lock, and two replacers with different reads, their statements interleaved, leave the union of both sets, which nothing reads again when the realtime read was the newer one. The refetches a burst causes are coalesced: the first event's at once, the rest once per one-second window, and a burst's split reads in one request per window (`lib/realtimeBatch.ts`) -- a second because another device's push sends one row per request, so its import arrives one round trip apart, and a shorter window coalesces nothing (200 events 300 ms apart: 200 refetches of each list under 250 ms, 61 under a second); the refetch every sync ends with is unchanged. What Supabase delivers, read from production's `realtime.apply_rls` and its Postgres Changes guide (2026-10-23): an `INSERT` or `UPDATE` is authorised per subscriber against the row as the table holds it when Realtime reads the change (a split through its parent's policy), so one deleted again before then is never delivered; a `DELETE` skips RLS and, with RLS on, carries the primary key alone, so the split listener hears every user's split deletes as bare ids, and acts only on one it can tie to a split of the user's held here; a `DELETE` never reaches a listener filtered on `user_id` while the tables keep the default replica identity, so a purge's or an old client's hard delete is the next pull's. Nothing is sent again for the time a channel was down (a backgrounded app, a dropped socket, a Realtime restart, or the Free plan's 100 messages a second, past which Realtime disconnects the project's sockets): the channel's status callback runs a full sync when it comes back after an error or a timeout (not before this device's first download), and logs a channel the server closed, which realtime-js does not rejoin. What remains: a split refresh whose read failed, that stopped between its `DELETE` and its `INSERT`s, or that read another device's re-split between its two requests (one request round trip of that device apart: the set is written empty, then rewritten by the read its `INSERT`'s own events start, and with those events lost the parent shows no splits until a pull lists it) is the next event's or the next pull's, which lists the parent unless a device clock running ahead of the server's makes it miss it (the clock-skew bullet above); a transaction moved between accounts elsewhere refetches only its new account's register (an `UPDATE`'s `old` carries the primary key alone), and Reports wait for the next sync.
